# 修复配方

每种配方对应 `failure-patterns.md` 中的一种故障模式。配方格式：

- **适用故障**: 对应 failure-patterns.md 的模式编号
- **前置条件**: 需要什么
- **步骤**: 逐步修复
- **修复前后对比**: 具体示例
- **验证**: 如何确认修复成功

---

## 配方 1: 拆分巨型 SKILL.md

**适用故障**: #1 巨型 SKILL.md

**前置条件**: 目标 Skill 的 SKILL.md 超过 500 行

**步骤**:

1. **识别主题聚类**: 通读 SKILL.md，把内容按主题分簇（如"设置步骤"、"核心流程"、"错误处理"、"高级配置"）
2. **提取非核心内容**: 每个主题簇创建一个 reference 文件：`references/{topic}.md`
3. **写入口内容**: SKILL.md 只保留：
   - 核心概念（为什么做、核心原则）
   - 主流程（最常见 80% 场景的步骤）
   - 路由表（什么时候读哪个 reference）
4. **添加加载顺序提示**: 每个 reference 前标注"**何时加载**: {场景}"
5. **目标**: SKILL.md < 200 行（复杂 Skill < 300 行）

**修复前后对比**:

```
修复前:
SKILL.md (800 行)
  - 所有内容都在一个文件里
  - 无路由表
  - Agent 从头读到尾，信息稀释

修复后:
SKILL.md (180 行)
  - 核心概念 + 主流程 + 路由表
references/
  ├── advanced-config.md
  ├── error-handling.md
  └── edge-cases.md
  - 每个文件 < 300 行，有目录
  - Agent 按需加载
```

**验证**: 用 Audit 模式重审第 2 层（上下文工程），确认评分从 Weak → Strong/Adequate。

## 配方 2: 修复描述失效

**适用故障**: #2 描述失效

**前置条件**: Skill 的 description 太宽泛或太窄

**步骤**:

1. **收集用户的真实说法**: 想想用户实际会怎么说话——写的不是"数据分析"而是"帮我看下这个上季度的 sales.csv"
2. **确定触发锚点**: 描述应包含：
   - 具体动作（Analyze / Transform / Generate / Review）
   - 具体输入类型（CSV files / git diffs / API schemas）
   - 触发关键词（用户可能用的词，含变体）
3. **加隐性触发**: "Also trigger when user uploads X without explicitly asking for Y"——覆盖用户不点名 Skill 但明显需要它的情况
4. **控制长度**: 描述不超过 1024 字符
5. **测试触发率**: 想 5 个应该触发的 prompt 和 3 个不该触发的 prompt，在脑中跑一下

**修复前后对比**:

```yaml
# 修复前
name: data-helper
description: Helps with data tasks

# 修复后
name: sales-data-analyzer
description: >
  Analyze sales/revenue CSV and Excel files to find patterns,
  calculate metrics, and create visualizations. Use when user
  mentions sales data, revenue analysis, profit margins, churn,
  ad spend, or asks to find patterns in business metrics.
  Also trigger when user uploads xlsx/csv with financial or
  transactional column headers.
```

**验证**: 用 skill-creator 的 description optimization pipeline 做触发达标率测试。

## 配方 3: 修复上下文过载

**适用故障**: #3 上下文过载

**前置条件**: SKILL.md 指示 Agent 无条件加载 references

**步骤**:

1. **对每个 reference 问**: Agent 在 80% 的场景下都需要这个吗？是 → 保留在 SKILL.md 内；否 → 只在特定场景加载
2. **按场景分类 references**:
   ```
   - 所有场景都需要的核心知识 → 放在 SKILL.md 里（精简版）
   - 特定场景才需要的 → references/ 里，加加载条件
   ```
3. **写路由表**: 在 SKILL.md 中添加路由表
   ```markdown
   ## 路由表
   | 场景 | 加载文件 |
   |------|---------|
   | 首次设置 | references/setup.md |
   | 遇到错误 | references/error-handling.md |
   | 高级配置 | references/advanced-config.md |
   ```
4. **给每个 reference 加加载条件**: 在 reference 文件头部写 "**何时加载**: {明确的场景描述}"

**修复前后对比**:

```
修复前:
SKILL.md 末尾写 "Also read references/a.md, references/b.md, references/c.md"
→ Agent 每次都三个全读

修复后:
SKILL.md 中有路由表，按场景分流
→ Agent 只在遇到错误时才读 error-handling.md
```

**验证**: 在不同场景下测试，确认 Agent 没有加载无关 reference。

## 配方 4: 消除隐性知识假设

**适用故障**: #4 隐性知识假设

**前置条件**: Skill 中存在"Agent 应该知道"但没写明的知识

**步骤**:

1. **找隐式假设**: 通读 SKILL.md，标注所有依赖"常识"或"默认做法"的指令
2. **转换策略**（按类型）:
   - 约定/规范 → 写入 instructions 或 references
   - 工具用法 → 提供具体命令/代码示例
   - 项目上下文 → 写入 references，在 SKILL.md 中引用
   - 领域知识 → 提供关键定义和反例
3. **给例子，不给原则**: "代码示例优于文字解释"（GitHub 对 2500+ AGENTS.md 的分析结论）
4. **关键知识放在 SKILL.md 顶部**: 前 3 段必须包含最重要的信息（"Lost in the Middle" 效应——Agent 对开头和结尾的记忆最好）

**修复前后对比**:

```
修复前:
"分析数据并生成报告"  ← Agent 怎么知道报告格式？分析哪些维度？

修复后:
"分析 CSV 中的销售数据，按以下维度拆解：
 - 时间趋势（按月）
 - 品类表现（按 revenue 排名）
 - 客户分层（RFM 模型）
输出格式见 references/report-template.md"
```

**验证**: 用 2 个不同的测试 prompt，确认输出形式一致。

## 配方 5: 添加验证步骤

**适用故障**: #5 无验证

**前置条件**: Skill 执行完就结束，没有自我检查

**步骤**:

1. **定义成功标准**: 什么算"做完了"？写 3-5 个可检查的断言
2. **嵌入验证步骤**: 在 Skill 流程末尾（或关键步骤之间）加入：
   ```markdown
   ## 完成前自检
   1. 输出是否符合 {具体格式要求}？
   2. 是否覆盖了 {关键维度}？
   3. 是否有 {常见遗漏项}？
   如果任一答案为否 → 修复后再提交
   ```
3. **对抗 first-plausible-solution bias**: 要求 Agent 对照需求（而非对照自己的代码）验证
4. **可选——添加断言**: 对于有脚本的 Skill，加入自动化断言

**修复前后对比**:

```
修复前:
3. 生成报告
4. 输出文件

修复后:
3. 生成报告
4. 自检：
   a. 报告是否包含所有 5 个必需章节？
   b. 每个数字是否有来源引用？
   c. 建议是否具体（不含"建议优化"这种空洞结论）？
   不通过 → 回到步骤 3 修复
5. 输出文件
```

**验证**: 故意给一个模糊的 prompt，确认 Agent 不会产生"看起来对但实际错"的输出。

## 配方 6: 消除硬编码

**适用故障**: #6 硬编码综合征

**前置条件**: Skill 中包含硬编码路径或项目特定内容

**步骤**:

1. **识别硬编码**: 搜索 SKILL.md 和 references 中的硬编码路径、文件名、项目名
2. **替换为模板变量**: 用 `{project_name}`、`{src_dir}` 等标记替代
3. **添加发现步骤**: 在 Skill 流程开头加入环境发现：
   ```markdown
   1. 先扫描项目结构，确认目录布局
   2. 根据实际布局调整后续步骤
   ```
4. **提供通用描述而非具体路径**:
   ```
   修复前: "打开 src/auth/login.ts"
   修复后: "找到认证模块（通常在 auth/ 或 authentication/ 下，含 login 入口函数）"
   ```

**验证**: 在不同项目结构下测试，确认 Skill 能自适应。

## 配方 7: 清理规则蔓延

**适用故障**: #7 约束蔓延

**前置条件**: SKILL.md 中规则越来越多，没有分类和优先级

**步骤**:

1. **审计现有规则**: 列出所有规则，标注每条规则的：
   - 触发频率（最近 10 次使用中，几次真的用到了？）
   - 可检查性（能被自动检查吗？还是只能靠人判断？）
2. **分类**:
   - **铁律**（必须遵守，违反 = 错误）→ 保留在 SKILL.md 靠前位置
   - **指南**（应该遵守，特殊情况下可以打破）→ 移到 references/，标注"判断优先"
   - **死规则**（从未触发或模型已不再犯）→ 删除
3. **清理标准**: 一条规则如果连续 5 次使用都没有被触发，就删除或降级
4. **写删除标准**: 每条保留的规则写一句"当 {条件} 时可以删除此规则"

**验证**: 对比清理前后 SKILL.md 行数，确认规则密度（每 10 行的有效规则数）提升。

## 配方 8: 定义子 Agent 边界

**适用故障**: #8 幽灵子 Agent

**前置条件**: Skill 提到使用子 Agent 但没有定义边界

**步骤**:

1. **对每个子 Agent 写协议**:
   ```markdown
   ## Subagent: {name}
   - **职责**: 单句描述
   - **输入**: 具体格式（JSON schema / 文件路径 / 自然语言描述）
   - **输出**: 具体格式
   - **边界**: 不能做什么（如"不修改文件，只读分析"）
   - **错误处理**: 出错时返回什么？主 Agent 接管还是重试？
   ```
2. **定义交接格式**: 子 Agent 之间传什么，用什么格式（JSON 优于 Markdown——Agent 更少意外编辑结构化数据）
3. **定义失败模式**: 子 Agent 超时/报错/返回空时主 Agent 做什么

**验证**: 模拟子 Agent 失败的场景，确认主 Agent 能正确处理。

---

## 配方 9: 构建错误模型

**适用故障**: #9 无错误模型

**前置条件**: Skill 只有 happy path，无错误处理

**步骤**:

1. **列举 top 5 失败场景**: 什么最可能出错？（依赖缺失、文件不存在、API 报错……）
2. **对每个场景定义行为**:
   - 可自动修复？→ 给修复步骤
   - 需要用户？→ 说明需要什么，问清楚再继续
   - 无法恢复？→ 告诉用户为什么，保存已完成的部分
3. **加入降级路径**: 如果 A 方案不行，B 方案是什么？
4. **写入 SKILL.md 或专门的 references/error-handling.md**:
   ```markdown
   ## 遇到错误时
   1. 判断错误类型（见下表）
   2. 按对应方式处理
   3. 不要静默失败——至少要告诉用户发生了什么
   ```

**验证**: 模拟缺文件、无网络等场景，确认 Skill 不卡死。

## 配方 10: 添加检查点

**适用故障**: #10 状态失忆

**前置条件**: Skill 涉及多步骤、长时间运行的任务

**步骤**:

1. **识别原子步骤**: 把一个完整任务拆成可独立完成、独立验证的原子步骤
2. **加进度文件**: 每完成一个原子步骤，记录到进度文件（如 `progress.md` 或 JSON）
   ```markdown
   ## 进度
   - [x] 步骤 1: 数据清洗
   - [x] 步骤 2: 特征工程
   - [ ] 步骤 3: 模型训练  ← 当前
   - [ ] 步骤 4: 结果输出
   ```
3. **加恢复逻辑**: SKILL.md 开头加上：
   ```markdown
   ## 启动时检查
   1. 检查是否有进度文件
   2. 如果有 → 从未完成的步骤继续，不重复已完成的步骤
   ```
4. **中间产物持久化**: 关键中间结果存为文件（而非仅在上下文中）

**验证**: 模拟会话中断后重连，确认能不重做已完成步骤。

## 配方 11: 补充确定性工具

**适用故障**: #11 工具不足

**前置条件**: Skill 让 Agent 用自然语言做重复性工作

**步骤**:

1. **识别重复性步骤**: Agent 每次都要重新写的代码 / 每次都要做的格式转换
2. **写脚本**: 把重复性、确定性工作写成 Python/JS/Bash 脚本，放入 `scripts/`
3. **在 SKILL.md 中引用**:
   ```markdown
   格式转换使用 `scripts/convert.py`，不要手写转换逻辑。
   ```
4. **脚本原则**:
   - 单一职责，一个脚本做一件事
   - 有错误码（非零 = 失败，Agent 能判断成功/失败）
   - 输出简洁（成功时静默或只输出关键信息，失败时才大声）

**验证**: 两次运行相同输入，确认输出一致。

---

## 配方 12: 固化输出格式

**适用故障**: #12 输出模糊

**前置条件**: Skill 没有规定输出格式

**步骤**:

1. **定义输出 Schema**: 用模板展示输出结构（不是 JSON Schema，是具体示例）
   ```markdown
   ## 报告结构
   必须使用以下结构：

   # [标题]
   ## 摘要（3 句话以内）
   ## 发现（每条发现含：问题、证据、影响）
   ## 建议（每条建议含：方案、优先级、预估改动量）
   ## 附录（数据来源、完整结果）
   ```
2. **给好例子和坏例子**: 各一个，让 Agent 知道边界
3. **加入输出验证**: 完成前检查输出是否符合模板结构

**验证**: 两次运行相同输入，输出结构一致。

---

## 配方 13: 添加路由表

**适用故障**: #13 无路由表

**前置条件**: SKILL.md 很长但没有告诉 Agent 何时读哪个 reference

**步骤**:

1. **在 SKILL.md 中添加路由表**（放在靠前位置）:
   ```markdown
   ## 路由表
   | 场景/任务 | 加载文件 | 何时加载 |
   |----------|---------|---------|
   | 首次使用 | references/setup.md | 第一次配置时 |
   | 核心流程 | （SKILL.md 正文已足够） | 每次 |
   | 遇到错误 | references/error-handling.md | 出错时 |
   | 高级配置 | references/advanced-config.md | 用户明确需要时 |
   ```
2. **给每个 reference 文件加加载条件**: 文件第一行写 `**何时加载**: {场景}`
3. **路由表放在 SKILL.md 前 50 行内**: 确保在上下文开头的高利用率区域

**验证**: 在不同场景下测试，确认只加载了相关 reference。

---

## 配方 14: 定义禁区

**适用故障**: #14 无禁区

**前置条件**: Skill 没有说明不做什么、不适用什么场景

**步骤**:

1. **写"不适用场景"**:
   ```markdown
   ## 不适用场景
   - 不适用于 {相邻但不相关场景}
   - 如果用户需要 {X}，应使用 {其他 Skill 或工具} 代替
   ```
2. **写"不要做"列表**: 列举 3-5 个最常见的错误行为
   ```markdown
   ## 不要做的事情
   - 不要修改 {边界外的文件}
   - 不要在不确定时猜测——先问用户
   - 不要跳过验证步骤
   ```
3. **明确与相邻 Skill 的边界**: 如果有功能类似的 Skill，写明职责划分

**验证**: 用边界外的 prompt 测试，确认 Skill 不会错误触发或产生错误输出。
