# 第 3 层：约束与守卫

**何时加载**: Audit、Prevent 模式；或诊断 Skill 的边界控制能力时。

**核心问题**: 边界清晰吗？规则被机械强制执行了吗？还是只靠"自觉"？

---

## 诊断问题

### 输出约束

1. 输出格式是否明确定义？（模板、schema、示例——至少有一种）
2. 定义的输出格式是否足够具体？（"生成报告"不是格式，"报告含 5 个章节: X, Y, Z"才是）
3. 是否有好输出和坏输出的对比示例？
4. 输出验证是否嵌入工作流？（完成前检查输出是否符合模板）

**优秀示例**: cython-pyd-reverse 的 "Final Deliverables"——明确规定输出 3 个 MD 文件，各有指定结构。

### 检查点

5. 关键步骤之间是否有检查点？（完成 A 后，验证 A 再进入 B）
6. 是否使用了强制停止机制？（如 🛑 标记——"在这里停下来，确认结果再继续"）
7. 检查点的验证标准是否具体？（"确认日志中没有 error" 比 "确认没问题" 好）

**优秀示例**: huashu-design 的 🛑 检查点——"Stop and ask user at these points"。

### 行为边界

8. 是否定义了"不该做什么"？（至少 3 条）
9. 是否说明了不适用场景？
10. 是否明确了与其他 Skill 的职责边界？
11. 是否有权限/安全边界？（如"不修改 src/ 之外的文件"）

**反例**: Skill 只说了"做什么"，没说不做什么——Agent 在模糊场景下越界的概率大幅上升。

### 规则质量

12. 每条强制性规则是否解释了"为什么"？（理解原因的规则比盲从的规则更可靠）
13. 规则是否有具体的触发场景？（"当你遇到 X 时，做 Y" 比 "总是做 Y" 更精确）
14. 规则是否可被自动检查？（理想情况：规则 = lint 检查 + pre-commit hook）
15. 是否有"规则过多"的问题？（见 failure-patterns.md #7 约束蔓延）
16. 是否有"为删除而构建"的意识？（每条规则有失效条件吗？）

### 对抗常见 Agent 偏见

17. 是否有对抗 "first plausible solution bias" 的机制？（见 fix-recipes.md 配方 5）
18. 是否防止 Agent "自信地编造"？（不确定时强制要求确认，而非猜测）
19. 是否防止 Agent "复制坏模式"？（如果代码库有坏模式，Skill 能提醒 Agent 不要学吗）

## 本层优秀模式

| 模式 | 来源 | 说明 |
|------|------|------|
| 铁律 vs 指南 | huashu-design | 硬规则（铁律）和软规则（指南）分开 |
| 🛑 检查点 | huashu-design | 关键节点强制停止验证 |
| 不适用场景 | huashu-design | 明确边界，防止越界触发 |
| 输出模板 | cython-pyd-reverse | 规定精确的输出文件数和结构 |

## 本层常见故障

1. **无约束**: 输出格式完全自由，每次结果不同
2. **规则无解释**: "你必须做 X" 但不解释为什么——Agent 在边缘情况无所适从
3. **规则过多**: 几十条规则堆砌，没有优先级，稀释核心约束
4. **无检查点**: Agent 一路跑到结束，中间没验证

## 评分指南

| 评分 | 标准 |
|------|------|
| **Strong** | 输出格式固化，有检查点，有禁区声明，规则有优先级和解释 |
| **Adequate** | 有输出格式和基本规则，但检查点和禁区不完整 |
| **Weak** | 规则模糊或过多，无优先级，无检查点 |
| **Missing** | 无输出约束，无行为边界，完全依赖 Agent 判断 |
