# 第 4 层：多 Agent 架构

**何时加载**: Audit、Prevent 模式；或 Skill 使用了子 Agent 时。

**核心问题**: 任务被有效分解了吗？子 Agent 的行为边界和交接协议清晰吗？

---

## 诊断问题

### 是否需要子 Agent

1. Skill 的任务是否真的需要子 Agent？（如果任务简单，子 Agent 是过度设计）
2. 是否需要的原因是基于实际复杂度，还是"看起来很酷"？
3. 如果没有子 Agent 环境（Claude.ai），Skill 能否降级到单 Agent 模式？

### 子 Agent 定义

4. 每个子 Agent 是否有清晰的职责边界？（一句话说清它做什么、不做什么）
5. 子 Agent 的 prompt 是否**自包含**？（不依赖当前对话上下文就能独立执行）
6. 子 Agent 的输入格式是否明确？（能是结构化的吗？JSON 比自然语言好）
7. 子 Agent 的输出格式是否明确？（能被主 Agent 可靠解析吗？）
8. 子 Agent 的行为边界是否明确？（"你可以读文件但不能写文件"）

**反例**: Skill 说 "用子 Agent 处理复杂任务" 但不定义子 Agent 的 prompt、输入输出、
错误处理——子 Agent 行为完全不可预测。

### Agent 间交接

9. 交接格式是否明确且结构化？（JSON 优于 Markdown——Agent 更少意外编辑结构化数据）
10. 交接信息是否包含状态？（成功了什么、失败了什么、下一步是什么）
11. 是否有防止信息在交接中丢失的机制？（结构化 > 自然语言摘要）

**参考**: Anthropic 的双 Agent 架构——初始化 Agent 输出 JSON 功能列表，编码 Agent 直接消费。

### 并行 vs 串行

12. 是否有明确的"何时并行、何时串行"的决策逻辑？
13. 并行任务之间是否有隔离？（git worktree、独立上下文、不共享可变状态）
14. 是否有并行度的上限？（无限制的并行 = 资源耗尽）

### 子 Agent 错误处理

15. 子 Agent 失败时主 Agent 做什么？（重试？跳过？降级？问用户？）
16. 子 Agent 是否有时限？（超时 5 分钟没完成 = 失败，而不是永远等）
17. 子 Agent 的输出是否被验证？（不能信任子 Agent 的输出，要验证）

---

## 本层优秀模式

| 模式 | 来源 | 说明 |
|------|------|------|
| 初始化 + 编码双体 | Anthropic | 初始化 Agent 规划 → 编码 Agent 逐个执行 |
| 结构化交接 | skill-creator | grader/analyzer 用精确的 JSON Schema 定义输出 |
| 上下文防火墙 | skill-creator | 子 Agent 独立上下文，只传结构化结果回主 Agent |

## 本层常见故障

1. **幽灵子 Agent**: 提到用子 Agent 但不定义行为边界（见 failure-patterns.md #8）
2. **过度分解**: 简单任务拆成 5 个子 Agent，协调成本大于执行成本
3. **交接泄露**: 非结构化交接导致信息在 Agent 间丢失
4. **无失败处理**: 子 Agent 报错时主 Agent 不知所措

## 评分指南

| 评分 | 标准 |
|------|------|
| **Strong** | 子 Agent 边界清晰，交接格式结构化，有并行/串行决策逻辑，错误处理完整 |
| **Adequate** | 子 Agent 有基本定义和输出格式，但边界和错误处理不完整 |
| **Weak** | 子 Agent 定义模糊，交接不明确 |
| **Missing** | 提到子 Agent 但没有定义（幽灵） |
| **N/A** | Skill 不使用子 Agent——这不是扣分项 |
