# 第 5 层：评估与反馈

**何时加载**: Audit、Prevent 模式；或诊断 Skill 的质量保障能力时。

**核心问题**: Skill 能测量自己的质量吗？有验证闭环吗？

---

## 诊断问题

### 自检机制

1. Skill 是否有完成前的自查清单？（不只是"看看对不对"，而是具体检查项）
2. 自查项是否可操作？（"确认所有数字有引用来源" 比 "确认质量" 好）
3. 自查是否覆盖了最常见的失败模式？
4. 自检失败后是否有修复指引？（告诉 Agent 去哪里找正确做法）

**优秀示例**: cython-pyd-reverse 的 "Self-check checklist"——完成前逐项验证。

### 成功标准

5. 任务的成功标准是否可量化？（"报告通过 lint 检查" 比 "报告质量好" 好）
6. 成功标准是否写在了 Skill 里？（不是靠用户每次提醒）
7. 是否有"达到什么标准才算完成"的明确定义？

### 对抗模型偏差

8. 是否存在对抗 "first plausible solution bias" 的机制？
   - Agent 倾向于接受第一个看起来可行的方案，不做深入验证
   - 解法：要求 "对照原始需求验证，而非对照自己刚写的代码验证"
9. 是否存在对抗 "确认偏差" 的机制？
   - Agent 倾向于寻找支持自己方案的证据，忽略反面证据
   - 解法：要求列出 "这个方案可能的 2 个风险"

### 评估与迭代

10. 是否有定量评估机制？（测试断言、通过率、耗时对比）
11. 是否可与 skill-creator 的 eval pipeline 集成？
12. 是否有基准数据？（with-skill vs without-skill 对比）
13. 是否记录了常见失败案例用于改进？

### 人工审核门

14. 是否有明确的人工审核触发点？（什么情况下必须停下等用户确认？）
15. 审核触发点是否合理？（太多了烦人，太少了失控）
16. 审核信息是否充分？（用户能否只看审核信息就做出判断？）

---

## 本层优秀模式

| 模式 | 来源 | 说明 |
|------|------|------|
| 自检清单 | cython-pyd-reverse | 完成前逐项验证，不通过则修复 |
| 量化评估 | skill-creator | evals.json + 断言 + with/without 对比 |
| 三明治推理 | LangChain | 规划（高推理）→ 实现（中推理）→ 验证（高推理） |
| 4 步循环 | LangChain | Plan → Build → Verify（对照需求）→ Fix |

## 本层常见故障

1. **无验证**: Skill 执行完就结束，输出质量靠运气
2. **自检空洞**: "确认代码功能正确"——空洞的标准，Agent 永远回答 "是"
3. **过度信任**: Agent 信任自己刚写的代码，不做独立验证
4. **无基准**: 不知道 with-skill 比 without-skill 好多少

## 评估管道建议

如果 Skill 有可自动检查的输出：
1. 准备 3-5 个标准测试 prompt（覆盖 normal + edge）
2. 定义每个 prompt 的断言（能自动化检查的 pass/fail 条件）
3. 跑 with-skill 和 without-skill 两组
4. 对比通过率、耗时、token 消耗

如果 Skill 的输出是主观的（设计、写作等）：
1. 准备 3 个测试场景
2. 人工评审 + 反馈
3. 迭代直到用户满意

## 评分指南

| 评分 | 标准 |
|------|------|
| **Strong** | 有自检清单，有成功标准，有定量评估或系统人工审核机制 |
| **Adequate** | 有自检但较空洞，有基本成功标准 |
| **Weak** | 自检缺失或空洞，无成功标准定义 |
| **Missing** | 无验证机制，"做完就好" |
