# 第 6 层：长时间运行任务

**何时加载**: Audit、Prevent 模式；或 Skill 涉及多步骤、长时间运行时。

**核心问题**: Skill 能在中断后恢复吗？长时间运行不会迷路吗？

---

## 诊断问题

### 进度管理

1. 任务是否被拆分为原子步骤？（每步可独立完成、独立验证）
2. 是否有进度记录机制？（文件、JSON、checklist——必须有持久化存储）
3. 进度记录格式是否结构化？（JSON > Markdown checklist > 自然语言日志）
4. 进度记录是否包含"当前状态"？（不只是"做了啥"，还有"下一步是啥"）

### 恢复机制

5. 会话中断后，新会话能否从进度文件恢复？（不重做已完成步骤）
6. 是否有启动检查流程？（"先检查是否有进度文件 → 有就恢复 → 没有就全新开始"）
7. 恢复时是否先验证环境仍然有效？（依赖没变？文件还在？）
8. 是否强制 Git 提交作为检查点？（提交 = 不可丢失的进度标记）

**参考 Anthropic 实践**: 编码 Agent 每次会话启动时的标准步骤：
1. `pwd` 确认工作目录
2. 读 git log 和进度文件了解最近工作
3. 读功能列表选择最高优先级未完成功能
4. 启动开发服务器
5. 跑基本 e2e 测试确认应用未处于损坏状态
6. 然后才开始实现新功能

### 上下文管理

9. 长时间运行是否会导致上下文腐烂？（Context rot——过多历史信息稀释当前任务）
10. 是否有上下文重置策略？（每个子任务新 session，或定期清理旧上下文）
11. 关键状态是否存储在上下文之外？（文件、git 提交、数据库——而非只在对话中）

### 错误恢复

12. 原子步骤失败后能否单独重试？（不影响已完成步骤）
13. 是否有"卡住检测"？（同一文件编辑超过 N 次 = 可能卡住了，需要换方案）
14. 是否有时限或预算？（无限运行 = 迟早出问题）

**参考 LangChain 实践**: LoopDetectionMiddleware——追踪同一文件编辑次数，
超过阈值注入 "Consider revisiting your approach"。

### 用户通知

15. 长时间任务是否有进度通知？（用户不需要一直盯着）
16. 关键里程碑是否通知用户？（"第 3/5 步完成，接下来是..."）
17. 异常情况是否及时告警？（"第 4 步遇到问题，已重试 2 次..."）

## 本层优秀模式

| 模式 | 来源 | 说明 |
|------|------|------|
| 初始化 + 编码双体 | Anthropic | 初始化 Agent 规划 JSON → 编码 Agent 逐个执行 + 更新进度 |
| JSON 功能列表 | Anthropic | JSON 追踪每个功能的 passes 状态 |
| 循环检测 | LangChain | 同文件编辑 > N 次 = 可能 doom loop |
| 原子步骤 + Git | Anthropic | 每完成一个功能 → 提交 → 提交历史 = 进度日志 |

## 本层常见故障

1. **状态失忆**: 无检查点，中断后从头开始（见 failure-patterns.md #10）
2. **上下文腐烂**: 长对话累积过多历史，Agent 迷失在噪声中
3. **Doom loop**: 同一步骤反复微调但无进展
4. **无预算**: Agent 无限循环直到用户手动干预

## 评分指南

| 评分 | 标准 |
|------|------|
| **Strong** | 有结构化进度记录 + 恢复机制 + 上下文重置策略 + 错误检测 |
| **Adequate** | 有基本进度记录和恢复机制 |
| **Weak** | 多步骤但无进度记录，中断后无法恢复 |
| **Missing** | 无检查点设计，长时间任务不可靠 |
| **N/A** | Skill 不涉及长时间运行任务——这不是扣分项 |
